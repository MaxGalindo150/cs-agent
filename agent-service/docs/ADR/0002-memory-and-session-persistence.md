# ADR-0002 — Memory & session persistence: PostgreSQL, an owned `agent` schema, SQLAlchemy + Alembic

- **Status:** Accepted
- **Date:** 2026-07-21
- **Deciders:** Maximiliano Galindo
- **Context service:** `agent-service` (EigenCore Customer Support)
- **Supersedes / relates to:** builds on ADR-0001 (harness). Unblocks `agent/memory` and `agent/runtime` (sessions), listed as *later phases* in `CLAUDE.md` §9.

---

## Context

ADR-0001 fixed the runtime shape (single agent + deterministic tools + hand-rolled harness) but
left the agent **stateless in memory**: it has no durable place to keep conversations or what it
learns. `CLAUDE.md` §9 names PostgreSQL as the state backend target and gates any schema/ORM/
migration work behind its own ADR. This is that ADR.

Constraints that shape the decision:

1. **Cloud Run is ephemeral and scales horizontally.** State cannot live in the process or on
   local disk — the next request may hit a different instance, and instances are recycled. A
   single-file store (e.g. SQLite on disk) breaks the moment concurrency > 1. State must live in
   a shared, networked store.
2. **A DB connection must never be held across an LLM call** (`CLAUDE.md` §3). LLM calls take
   6–30s; the prior platform exhausted its pool this way. Persistence is short, per-statement
   pool calls only — no transaction spans a provider call.
3. **Single-tenant first** (`CLAUDE.md` §9). No `tenant_id`, no RLS, no org hierarchy yet — but
   the design must be able to *grow* into multi-tenancy without a rewrite.
4. **The DB already exists.** The parent monorepo's `docker-compose.yml` runs
   `pgvector/pgvector:pg18` (Postgres 18 + pgvector ≥ 0.8, required by `docs/rag-design.md`),
   database `chatbots_platform`. This database is **shared** across platform services.

Because the database is shared, "isolate this service from other services" is a real question.
Alembic isolates the *evolution* of our slice (our own migration history and version table); the
*data* boundary is provided by giving this service its own PostgreSQL **schema**.

## Decision

Persist agent memory and sessions in **PostgreSQL**, inside a **dedicated `agent` schema** of the
shared `chatbots_platform` database, via **SQLAlchemy (async) + Alembic**.

1. **Owned schema = isolation boundary.** All agent-service tables live under `agent.*`. No other
   service reads or migrates our tables; we do not touch theirs. Alembic is configured with
   `version_table_schema="agent"` so our migration lineage is fully independent.
2. **Async access, short connections.** Access goes through `asyncpg` + SQLAlchemy async engine
   with a pool. Every read/write is a short, per-statement pool call. **No connection is held
   across an LLM call** — this is a hard rule, enforced by keeping persistence out of the harness
   loop's provider-call span.
3. **Four tables** (see schema below): `chat_sessions`, `chat_messages` (raw log for
   consolidation), `facts` (semantic memory), `episodes` (episodic memory). `calendar_events` and
   any tool-artifact tables are **deferred** until the tool that writes them exists — no
   speculative schema.
4. **Full-text search is native, no triggers.** Retrieval over `facts`/`episodes` uses a
   generated `tsvector` column with `to_tsvector('spanish', …)` and a `GIN` index. This replaces
   SQLite's FTS5 + hand-written insert/delete/update triggers with a single generated column the
   database maintains automatically. Content is Spanish (Cashea, a BNPL service for a
   Spanish-speaking market).
5. **UUID primary keys.** Application-generatable, safe to expose, no cross-instance coordination.
   (Time-ordered UUIDv7 is an option for index locality; not required to start.)
6. **Single-tenant, growth-ready.** No `tenant_id`/RLS now. The path to multi-tenancy is a later
   ADR: add `tenant_id` columns + row-level security over this same schema — an additive
   migration, not a redesign.
7. **pgvector deferred.** The extension is available (rag-design.md), but semantic-embedding
   retrieval is out of scope here. Full-text (`tsvector`) is the retrieval mechanism for now.

### Schema (`agent` schema)

```
agent.chat_sessions
  id                uuid        PK
  title             text
  created_at        timestamptz NOT NULL default now()
  last_activity_at  timestamptz NOT NULL default now()

agent.chat_messages           -- raw conversation log; consolidation reads from here
  id                uuid        PK
  seq               bigint      NOT NULL  GENERATED BY DEFAULT AS IDENTITY  -- see Amendment 1
  session_id        uuid        NOT NULL  FK -> agent.chat_sessions(id) ON DELETE CASCADE
  role              text        NOT NULL  -- 'user' | 'assistant'
  content           text        NOT NULL
  meta              jsonb                 -- per-turn telemetry: gate decision, latency, tools, iterations
  consolidated      boolean     NOT NULL default false
  created_at        timestamptz NOT NULL default now()
  INDEX (session_id, created_at)

agent.facts                    -- semantic memory: durable facts about the user/people/projects
  id                uuid        PK
  subject           text        NOT NULL  -- who/what the fact is about
  content           text        NOT NULL
  source            text        NOT NULL default 'user'  -- 'user' | 'consolidation'
  created_at        timestamptz NOT NULL default now()
  content_tsv       tsvector    GENERATED ALWAYS AS (to_tsvector('spanish', subject || ' ' || content)) STORED
  GIN INDEX (content_tsv)

agent.episodes                 -- episodic memory: dated things that happened (distilled)
  id                uuid        PK
  happened_at       timestamptz NOT NULL  -- when the episode occurred
  summary           text        NOT NULL
  created_at        timestamptz NOT NULL default now()
  summary_tsv       tsvector    GENERATED ALWAYS AS (to_tsvector('spanish', summary)) STORED
  GIN INDEX (summary_tsv)
```

### Amendment 1 (2026-07-22) — conversation order is a sequence, not a timestamp

Building the access layer surfaced a latent ordering defect. `created_at` defaults to
`now()`, which in PostgreSQL is the **transaction** timestamp: messages written in one
transaction share an identical value, and the tiebreak fell to a random UUID — so history
could come back in arbitrary order. Ordering the model's context by luck is not acceptable.

`chat_messages` therefore carries a `seq` identity column, and all message queries order by
it. This gives a total, monotonic insertion order that does not depend on the clock or on
transaction boundaries (migration `0002`; the index becomes `(session_id, seq)`).

In practice production would rarely have hit this — the "no DB connection across an LLM call"
rule already forces user and assistant turns into separate transactions — but the guarantee
now comes from the schema instead of an incidental property.

## Consequences

**Positive**
- Request path stays **stateless**: state lives in Postgres, so horizontal scaling on Cloud Run
  is safe. Nothing assumes a single long-lived instance.
- **Data isolation** from sibling services via the owned `agent` schema; **migration isolation**
  via an independent Alembic history. Either can evolve without coordination.
- Full-text retrieval with **no triggers to maintain** — the generated column and GIN index are
  managed by the database. Deterministic, unit-testable (assert on rows) per the L1 eval strategy.
- Sessions are a **first-class entity** (`chat_sessions`), enabling "new chat" / session switching
  and clean per-session history assembly in `agent/runtime`.
- Additive path to multi-tenancy; no redesign required later.

**Negative / costs**
- We own SQLAlchemy models + Alembic migrations and their review discipline (versioned SQL,
  reversible where practical).
- A single `to_tsvector` dictionary per column: **Spanish-only** full-text. Mixed-language content
  would degrade stemming/stopword handling and needs a separate decision (per-language column or a
  language column) — explicitly out of scope now.
- Connection-lifetime discipline ("never across an LLM call") is a rule the code must uphold; it
  is not enforced by the type system. Covered by code review and the access-layer design.

## Alternatives considered

- **SQLite single-file store (the Waku/Hermes shape).** Rejected for this service: dies with the
  instance, not shared across instances, breaks under Cloud Run concurrency; FTS5 + manual
  triggers + hand-rolled `ALTER TABLE` migrations do not port to the Postgres target. The *memory
  model* (facts / episodes / raw log) was kept; the engine and single-file assumption were not.
- **Separate database per service** (instead of a schema in the shared DB). Rejected for now:
  heavier ops for no benefit at single-tenant scale; a schema gives sufficient isolation and can
  be promoted to a separate database later if needed.
- **A single flat `chat_log` table** (Waku's shape). Rejected: sessions are central to the
  `agent/runtime` design; modeling `chat_sessions` + `chat_messages` explicitly is clearer and
  matches how the product surfaces conversations.
- **pgvector / embedding retrieval from day one.** Deferred: adds an embedding dependency and cost
  before it is needed; `tsvector` covers current retrieval. Revisit under its own ADR.

## Reversal

Storage sits behind an access layer (repositories), not called directly from the harness. If
Postgres proves wrong (e.g. a managed vector/memory service wins), replace the repository
implementations behind the same interfaces and supersede this ADR; the harness and business rules
are unaffected. Schema changes are versioned Alembic migrations, so forward/rollback is explicit.
